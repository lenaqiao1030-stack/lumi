## 一、一句话介绍

Lumi 是一个从「每日个性化报纸」切入、逐步成长为「全面接管生活的个人助理」的 Agent 产品。用户每天早上收到一份 5 分钟读完的定制报纸,可以随时把其中任何一条变成提醒、摘要或持续追踪的任务。

**面试 30 秒版本**:我做的是一个个人 Agent,用「每日报纸」解决信息焦虑这个高频刚需,再用「聊聊 → 任务」把阅读自然转成行动。同时它也是我学习 Claude Code 底层设计(Agent loop、工具系统、权限治理、子 Agent、定时任务、Skill/MCP)的实践载体,每个产品功能都对应一个架构概念。

## 二、用户的真需求 ✅

个人助理产品的生死在第 2 到 14 天,用户明天为什么还会打开?四层需求:

1. **安心感**:今天没有漏掉重要的事(对抗信息焦虑)
2. **省时间**:5 分钟读完,而不是刷 1 小时
3. **能行动**:看到信息后,顺手变成待办、提醒或追踪
4. **被了解**:它记得我,越用越准

## 三、核心体验链路 ✅

1. **落地页**:欢迎 + 选择是否带声音进入(声音默认关,动画可跳过,老用户直接进入)
2. **开屏动画**:粒子形态的 Lumi 自我介绍,像游戏剧情对话一样引导
3. **三问引导**:怎么称呼你、做什么工作、关心哪些领域(选项 + 打字)。其余偏好通过使用行为学习,目标 60 秒内看到第一份报告
4. **现场出报告**:等待态做成 Agent loop 的可视化(「正在搜索 AI 芯片… 正在读 12 篇文章…」),既建立信任又掩盖延迟
5. **全屏阅读**:固定 N 条,每条可「收藏 / 不感兴趣 / 聊聊」
6. **聊聊 → 任务**:带着这条卡片的引用回到聊天界面,输入框附近出现任务提示语(提醒我 · 周四上午 / 读完给我 3 行摘要 / 持续追踪),点击后先出**确认卡**,Agent 复述理解,用户确认后才执行
7. **收尾动效**:读完关闭报纸,猫头鹰Lumi衔着小报纸飞向信箱图标,回到主界面

### 补充的关键设计 ✅

- 每条标注**为什么推给你**,以及来源数量和原文链接
- 报纸有终点,有「今日已读完」的完成感,这是对抗无限信息流的差异化卖点
- 冷启动:第一份报告混入 1 到 2 条探索内容;反馈细分为「太浅 / 太深 / 已经知道了 / 少推这个话题」
- **渐进授权**:通知、日历、邮箱等权限延后到有具体场景时再请求
- **信箱(Inbox)是所有异步产出的统一入口**:每日报纸、追踪话题更新(有更新才推)、任务结果、待审批事项。猫头鹰是「信使」品牌
- 留存:次日预告、有更新才通知、周回顾,轻连续性,不做打卡压力
- 信任与治理:记忆可见可编辑、Agent 行为有日志、权限分级(只读搜索 → 写入待办 → 发消息需逐次确认)
- 真实场景:手机端为主、语音播报版、一键分享、暂停/假期模式、成本控制与免费版边界

## 四、报告内容设计 ✅

### 信息金字塔:默认只给最浅一层

| 层级 | 内容 | 阅读时间 |
| --- | --- | --- |
| L0 封面 | 一句话总览 + 条数与时长 + 最重要的一件事 | 5 秒 |
| L1 卡片 | 结论式标题 + 与你相关 + 配图 | 每条 10 秒 |
| L2 展开 | 3 个要点 + 背景 + 多方观点 + 原文链接 | 1 到 2 分钟 |
| L3 聊聊 | 进入对话深挖 | 不限 |

### 单条卡片约束

- 标题写结论,不抄原标题,≤20 字
- 「与你相关」1 句,≤30 字
- 要点最多 3 条,每条 ≤25 字
- 能图表化的用一个高亮数字或小图,不用文字
- 2 到 3 个来源可点开
- 固定 7±2 条:必看 3 + 值得看 3 + 惊喜 1(防信息茧房)
- 没大事时诚实说「今天 XX 领域没有值得看的」

### 多领域展示:一份报纸,不是多个 Tab

- **头版**:跨领域最重要的 Top 3,按重要性而非领域排序
- **分版**:每个领域 2 到 3 条,按用户权重分配,每个领域至少 1 条保底
- **副刊**:跨领域关联、一条彩蛋
- 视图可切换「按重要性 / 按领域」;领域超过 5 个时分核心(每日)与次要(每周聚合)
- 同一事件跨领域时合并为一条并标注「同时涉及 A、B」
- 领域权重由用户行为自动调整,用户可见可改

## 五、名词解释:什么是「卡片(Card)」

**卡片是报纸里的最小内容单元:一条新闻或一个话题,经 Agent 加工后形成的一份结构化小档案。** 它不是原文转载,而是 Agent 阅读多个来源后,写出的「结论标题 + 与你相关 + 最多 3 个要点 + 一个高亮数字 + 来源 + 可执行的下一步」。

- 用户每次翻页看到的就是一张卡片;「收藏 / 不感兴趣 / 聊聊」的对象也是一张卡片
- 一份报告(Report)= 封面 + 若干版面(Section)+ 若干卡片(Card)
- 卡片是系统里最重要的**数据单元和反馈单元**:前端展示它,反馈信号绑定它,聊天通过引用(card\_ref)读取它,任务从它的 suggested\_tasks 生成
- 类比:报纸是文章的集合,Lumi 的报告是卡片的集合,版面只是卡片的不同排列方式

## 六、数据结构设计 ✅

### 设计原则

1. **内容与版面分离**:Agent 只输出语义字段,版面由前端决定,换端(手机/语音/邮件)不改 Agent
2. **字数限制写进 schema**:超限触发改写重试,而不是靠 prompt 祈祷
3. **每个论断可溯源**:要点必须挂 source\_refs,无来源不允许出现
4. **卡片自带下一步动作**:suggested\_tasks 在生成卡片时一并产出
5. **所有 ID 稳定**:卡片、事件、话题都有 ID,反馈、追踪、去重、聊天引用才能串联

### Report 关键字段

- `status`: complete / degraded / failed;`meta.degradations` 记录降级项,失败可见
- `cover`: 一句话总览、总条数、预计阅读时长、头条卡 ID、主插画
- `sections`: 只引用 card\_ids,卡片平铺存放,所以「按重要性 / 按领域」切换不改数据
- `empty_domains`: 「今天没事」是一等公民
- `meta.stats`: 查询数、读页数、候选数、入选数

### Card 关键字段

- `tier`: must\_read / worth\_reading / surprise
- `event_id`: 跨源、跨领域去重键
- `why_signal`: 记录这条为什么被选中(interest / tracked / explore / trending),用于后续分析推荐有效性
- `key_points[].source_refs`: 来源挂在要点级别,可定位到原文
- `highlight`: number / delta / timeline / compare
- `confidence`: single\_source / multi\_source / official,单一来源要标注
- `detail`: L2 内容,允许懒生成以省成本
- `suggested_tasks`: 预填参数的任务模板

### 反馈事件

- 显式:save / dismiss / chat / too\_shallow / too\_deep / already\_known / less\_of\_topic / shared
- 隐式:dwell\_ms、depth\_reached、source\_opened(显式反馈稀疏,隐式信号同样重要)

### 聊聊与任务衔接

- 聊聊传 `card_ref`(引用),不传文字拷贝,Agent 自行读取卡片
- 任务确认卡含 `understood_as`(自然语言复述)、`output_to`(结果去向)、`permissions_needed`(权限声明)、`status: pending_confirm`

## 九、日报生成流水线 ✅

日报由 9 个阶段组成:研究、选材、写作分离,只有总编辑用大模型,检索结果按领域共享,到点先发布已完成部分。

### 流程

1. **加载上下文**:画像、领域权重、追踪话题、昨日已推内容、近期反馈
2. **Planner 规划**:每个领域的查询词、时间窗、配额,预留 1 个探索位
3. **并行检索**:每个领域一个 subagent,只输出候选事件,不写成稿
4. **合并去重**:事件聚类生成 event\_id,跨领域合并,剔除近几天已推
5. **总编辑筛选排序**:定 tier、头版、副刊、空领域
6. **并行写作**:每张卡片一个 Writer,只依据该事件的来源材料
7. **校验 Hook**:不合格则带着具体错误重试,最多 2 次
8. **并行配图**:封面主插画 + 单卡小图,失败用模板图
9. **组装发布**:生成 Report JSON,入 Inbox,推送

### 各阶段分工

| 阶段 | 工具 | 模型档位 | 并行方式 |
| --- | --- | --- | --- |
| Planner | 读画像与记忆 | 中档 | 否 |
| 领域研究员 | web\_search、web\_fetch | 小档 | 按领域并行 |
| 合并去重 | 代码 + embedding,不用 LLM | 无 | 否 |
| 总编辑 | 读候选池 | 大档 | 否 |
| Writer | 无,只读材料 | 中档 | 按卡片并行 |
| 校验 | 代码,不用 LLM | 无 | 按卡片并行 |
| 配图 | 图像生成 / 模板库 | 图像模型 | 与写作、校验流水衔接 |

### 三个关键决策

- **共享候选池**:同一领域的检索与去重每天只跑一次,所有用户共用;个性化只发生在总编辑选材和 Writer 写作阶段。用户越多,单人成本越低
- **截止时间驱动**:临近送达时刻仍未完成,先发布已完成部分,其余后补,不让用户空等
- **首次体验快速通道**:新用户首份报告只出 5 条,减少来源数,头版优先生成并优先展示,其余在阅读时继续生成

### 失败降级

| 故障 | 处理 | 报告状态 |
| --- | --- | --- |
| 某领域搜索超时 | 用已有结果继续;完全无结果则放入 empty\_domains 并说明 | degraded |
| 候选不足 | 先放宽时间窗到 72 小时,再用探索内容或追踪话题补位,仍不够就出短版并如实说明 | complete |
| 数字或来源核查失败 | 删掉该要点;整张卡不成立则丢弃,换候补卡 | complete |
| Writer 连续重试失败 | 回退为「原标题 + 摘要」的朴素卡片,confidence 标注 | degraded |
| 配图失败 | 用模板图或纯排版卡,记入 degradations | degraded |
| 临近送达时刻未完成 | 先发布已完成部分,其余后补 | degraded |
| 整体失败 | 推「今日简报延迟」,后台重试 | failed |

### 成本控制

- 模型分级:只有总编辑用大档,研究员和 Writer 用小中档
- L2 的 detail 懒生成:用户展开时才生成,生成后缓存
- 预算上限:每个 subagent 限制最大查询数、读页数和时长,超限带着已有结果返回
- 研究员只找料不写稿,总编辑在统一标准下取舍,Writer 只能基于已取得的材料写,降低编造风险

### 对应 Claude Code 概念

| Lumi 的设计 | Claude Code 对应 |
| --- | --- |
| Planner 先出计划再执行 | Plan mode |
| 领域研究员,独立上下文、受限工具集 | Subagent |
| 总编辑统筹研究员和 Writer | Agent Team 的 lead |
| 校验后不合格就重试 | Hook + 反馈回路 |
| 预算上限 | max turns / token budget |
| 每日触发 | Schedule(cron) |
| 降级与截止发布 | 失败隔离、部分结果返回 |

## 十、Agent loop、Tool System 与 Governance ✅

工具按副作用分级,权限逐级收紧,读网页的 Agent 没有任何写入工具,所有拦截与审计由确定性 Hook 完成。

### Agent loop

两类 loop 共用同一套引擎:后台 loop(日报流水线,由 Schedule 触发,无人值守)和对话 loop(用户聊天,遇到需确认的动作就暂停等用户)。

1. 输入:用户消息 / 定时触发 / card\_ref
2. 组装上下文:系统提示 + 记忆 + 引用卡片
3. 模型输出文字或工具调用
4. PreToolUse Hook → 权限判定 → 执行工具 → PostToolUse Hook
5. 结果回填上下文,继续循环
6. 终止:模型不再调工具 / 达到最大轮数 / 预算用尽 / 用户中断

- 每一步向前端发事件(searching / reading / tool\_call / waiting\_confirm),首次体验的「正在搜索…正在读 12 篇文章…」就是这些事件的可视化
- 终止条件(最大轮数、token 预算、超时)写死在引擎里,不靠模型自觉停下

### Tool System

每个工具的定义字段:

| 字段 | 作用 |
| --- | --- |
| name / description / input\_schema | 模型据此决定怎么调用 |
| side\_effect | read / write\_internal / write\_external / destructive,权限判定依据 |
| idempotent | 重试是否安全 |
| concurrency\_safe | 能否并行执行(只读工具可以) |
| timeout / cost | 预算与超时控制 |

工具清单:

| 类别 | 工具 | side\_effect |
| --- | --- | --- |
| 信息获取 | web\_search、web\_fetch、read\_card、read\_report、search\_memory | read |
| 内部写入 | create\_task、set\_reminder、track\_topic、save\_memory、update\_preference | write\_internal |
| 对外动作 | send\_push、send\_email、calendar\_write(后期经 MCP 接入) | write\_external |
| 生成 | generate\_image | read(只产生成本) |
| 编排 | spawn\_subagent、schedule\_task | write\_internal |
| 交互 | ask\_user(出确认卡、问澄清问题) | read |

按角色分配工具(最小权限):

| 角色 | 可用工具 |
| --- | --- |
| 领域研究员 | 只有 web\_search、web\_fetch |
| Writer | 没有工具,只读传入的材料 |
| 总编辑 | read\_card、search\_memory |
| 对话 Agent | 全部,但写入类要过权限 |

### Governance

**权限分级(按 side\_effect):**

| 级别 | 例子 | 默认策略 |
| --- | --- | --- |
| L0 只读 | 搜索、读卡片 | 自动放行 |
| L1 内部写入 | 建待办、设提醒、追踪话题 | 出确认卡,用户可勾选「以后这类自动执行」 |
| L2 对外动作 | 发邮件、写日历、发消息 | 每次确认,不可设为自动 |
| L3 不可逆 / 涉及钱 | 支付、删除数据 | MVP 阶段不提供 |

规则按 allow / ask / deny 存储,优先级 deny > ask > allow,存在用户设置里,可见可改(对应 Claude Code 的权限模式)。MVP 只做 L0 到 L2。

**Sandbox 三层隔离:**

1. 能力沙箱:每个 Agent 只拿到该角色的工具
2. 数据沙箱:所有读写强制带 user\_id,记忆与任务互相隔离;共享候选池不含个人数据
3. 资源沙箱:每个 Agent 有轮数、token、时长、速率上限

**防提示注入(最关键的安全设计):** 网页内容不可信,可能藏有劫持指令。对策是读写分离:读网页的研究员没有任何写入工具,它的输出只作为数据向下游流动,不作为指令;所有工具返回内容在上下文里标记为 untrusted。

**Hook(确定性代码,不用 LLM):**

| 事件 | 用途 |
| --- | --- |
| PreToolUse | 参数校验、权限判定、频率限制,可拦截或改写 |
| PostToolUse | 清洗结果、写审计日志、统计成本 |
| OnCardDraft | 卡片 schema 校验 |
| PreSend | 推送前检查免打扰时段、每日推送上限 |
| SessionStart | 加载记忆与偏好 |
| OnFeedback | 把反馈事件转为记忆更新 |

**审计与可撤销:** 每次工具调用记录谁(哪个 Agent)、什么工具、参数、结果摘要、权限判定、成本。用户端展示为「Lumi 做了什么」时间线,可撤销的动作带撤销按钮。

**完整例子「周四上午提醒我」:** 用户点任务提示语 → 对话 Agent 调用 set\_reminder → PreToolUse 命中 L1,判定 ask → loop 暂停,前端出确认卡(复述 + 可编辑时间)→ 用户确认(可选「以后提醒类自动执行」)→ 执行 → PostToolUse 写审计日志 → 结果进 Inbox → loop 继续并回复。

## 十一、Work System ✅

Task 是定义,Run 是每次执行;追踪话题默认沉默;Lead 统筹、Worker 不互相对话;Run 先写草稿再原子提交。

### Task 与 Run

Task 是用户委托事项的定义(做什么、何时做、结果去哪),Run 是它的某一次实际运行。一次性提醒是 1 个 Task + 1 个 Run;持续追踪是 1 个 Task + N 个 Run;每日日报是系统级 Task。重试、失败、审计、成本统计都落在 Run 上。

Task 种类:remind、digest、track、research、todo。

Task 状态机:

```
draft → pending_confirm → active ⇄ paused
                            ↓
                  done / cancelled / expired
```

Run 状态机:

```
queued → running → succeeded
            ↓  ↘ waiting_user(等确认或补充信息)
         failed → retry(仅幂等任务,最多 N 次)→ dead(进 Inbox 告知用户)
```

### Schedule

| 触发 | 例子 | 说明 |
| --- | --- | --- |
| 时间 | 周四 10:00 提醒;每日 6:30 出报 | 一次性或 cron,按用户时区 |
| 事件 | 追踪话题出现重大更新 | 由追踪 Run 的判断结果触发 |
| 手动 | 用户点「现在就跑一次」 | 优先级最高 |

- 幂等键 = task\_id + scheduled\_for,调度至少执行一次,靠幂等键防重复推送
- 错过策略因任务而异:提醒补发并注明「迟到了」;日报不补昨天的,直接出今天的
- 早晨高峰削峰:凌晨先跑共享候选池,再按用户送达时间错峰做个性化组装
- 队列优先级:对话交互 > 用户定时任务 > 日报生成 > 后台追踪;每用户有并发上限,搜索 API 全局限流,超限排队不丢弃

### 追踪话题:默认沉默

1. 每次 Run 搜上次之后的新内容,与任务状态(last\_seen\_event\_ids + 滚动摘要)比对
2. 判断是否重大(新事件、关键数字变化、官方发布);不重大则静默,日志记「已检查,无更新」
3. 重大则生成一张带 tracked\_topic\_id 的卡片进当天报纸(why\_signal = tracked);特别紧急且当日推送额度未用完才即时推送
4. 检查频率自适应:话题活跃则高频,冷了则降频
5. 自动提议收尾:事件结束或用户 N 天无互动时,提示「要停止追踪吗?」

### Subagent 与 Agent Team

Subagent 生命周期:spawn(角色、工具白名单、预算、输入契约)→ 独立上下文运行 → 只返回结构化结果,不返回完整对话 → 父 Agent 校验 schema → 销毁。

- 失败隔离:一个 subagent 超时或报错只影响它负责的那一块,父 Agent 收到 status + 部分结果
- 可取消:用户中断或任务取消时向下级联取消
- Lead 统筹,Worker 之间不直接对话:日报里总编辑是 lead,研究员和 Writer 只和它交换数据,流程可调试、可重放
- 共享数据放「黑板」(候选池、报告草稿),按字段所有权写入
- 后期 research 深度调研可组成小团队:规划员、多个研究员、事实核查员、写作员

### Remote 与 Worktree

- **Remote**:Agent 全部运行在云端,App 和网页只是视图,订阅事件流(SSE / WebSocket);用户关掉 App 任务照常运行,结果经 Bridge(APNs / FCM 推送、邮件)送达 Inbox
- **Worktree**:Claude Code 给并行 Agent 各一份隔离的工作副本。Lumi 的对应问题是多个 Run 同时写同一用户的待办、记忆、报告,做法是每个 Run 有自己的运行工作区先写草稿,成功后原子提交(日报 draft → published,带版本号);共享数据用乐观并发,版本冲突则重试或合并

### Inbox 条目类型

| 类型 | 来源 | 需要用户操作 |
| --- | --- | --- |
| report | 每日报纸 | 阅读 |
| track\_update | 追踪话题更新 | 阅读,可聊聊 |
| task\_result | 研究或摘要任务结果 | 阅读 |
| approval\_request | Run 执行中需要确认 | 是,确认或拒绝 |
| system\_notice | 任务失败、权限变更、额度提示 | 视情况 |

## 十二、记忆系统 ✅

记忆是 Lumi 的「被了解」:能用代码算的不让 LLM 写,每条记忆都有来源,用户看得见、改得了、忘得掉。

### 三层记忆

| 层 | 内容 | 谁写 | 例子 |
| --- | --- | --- | --- |
| 画像 Profile | 用户亲口给的稳定信息 | 用户(引导、设置) | 称呼、职业、关注领域、送达时间、阅读时长、深度偏好、屏蔽词、语言 |
| 兴趣模型 Interest | 从行为推出的数值化偏好 | 代码(OnFeedback Hook) | 领域权重、话题得分、来源偏好、深度倾向 |
| 事实 Facts | 对话和任务中出现的自然语言事实 | LLM 提取,经规则把关 | 「在做 AI 产品」「下周四要去发布会」 |

任务状态(追踪话题的滚动摘要等)属于 Task,会话上下文是临时的,二者都不算记忆。

### 生命周期

捕获 → 提取候选 → 校验(去重、冲突、敏感检查)→ 存储 → 检索 → 使用 → 衰减/过期 → 用户编辑/遗忘

### 写入策略

| 来源 | 写入哪层 | 策略 |
| --- | --- | --- |
| 引导和设置 | 画像 | 直接写 |
| 用户明确说「记住…」 | 事实 | 直接写,提示「已记住:… \[撤销\]」 |
| 反馈事件 | 兴趣模型 | OnFeedback Hook 按公式更新 |
| 对话中的推断 | 事实(候选) | 先作候选,同类证据累计到阈值(如 3 次)才转正,或请用户确认 |
| 网页或搜索结果内容 | 永不写入记忆 | 防止被恶意内容污染 |

- 敏感类别(健康、财务状况、精确位置、感情关系、宗教政治倾向)默认不自动记,除非用户明确要求
- 新的明确陈述覆盖旧的,旧的保留为历史(supersedes);画像优先于行为推断
- 兴趣得分带时间衰减(半衰期约 30 天);事实可带过期时间(过了周四,「周四发布会」自动失效)

### 使用:按需注入

| 使用方 | 取什么 |
| --- | --- |
| Planner | 领域权重、话题得分、屏蔽词 |
| 总编辑 | 权重、近期反馈、昨日已推 |
| Writer | 深度偏好、语言、称呼 |
| 对话 Agent | 画像摘要常驻(约 300 token)+ search\_memory 按需检索相关事实 |

记忆占上下文有预算上限,检索结果标注来源,作为参考数据而不是指令。

### 反馈如何更新兴趣模型

| 事件 | 影响 |
| --- | --- |
| save | 话题得分 + |
| chat | 话题得分 ++,可建议追踪 |
| dismiss | 话题得分 − |
| less\_of\_topic | 话题得分 −−,配额降低 |
| already\_known | 对该事件无惩罚,提高该话题的新颖度门槛 |
| too\_shallow / too\_deep | 调整深度偏好 |
| 停留时间、展开层级 | 隐式信号,小幅 +,权重远低于显式 |

- 领域配额由权重算出,每个领域保底至少 1 条
- 探索位优先选不确定性高的话题,探索条同时是校准信号
- 冷启动:引导里选的领域给初始先验,前 7 天学习率调高,随后降低
- 领域权重对用户可见、可拖动调整,手动调整优先于自动学习

### 可见、可编辑、可遗忘

「Lumi 记得你什么」页面:画像可直接改;兴趣显示权重条,可拖动或「不再推」;事实列表显示来源(如「来自 11 月 20 日你对卡片《…》的聊聊」)、置信度、过期时间,可编辑和删除;待确认候选一键「对」或「不对」。

- 报纸每条的「为什么推给你」可点开,链接到对应记忆记录
- 遗忘是真删除,同时清掉衍生数据(向量索引、兴趣得分中该事实的贡献)
- 聊天里提供「这次不要记住」(无痕模式),支持一键导出、一键清空
- 记忆写入同样进审计日志

### 对应 Claude Code 概念

| Lumi 的设计 | Claude Code 对应 |
| --- | --- |
| 画像,用户手写、优先级最高 | CLAUDE.md |
| 事实,自动提取,带来源 | auto memory |
| 记忆页,可看可改 | /memory 命令 |
| search\_memory 按需检索 | 按需读取,而不是常驻全文 |
| OnFeedback、SessionStart、会话结束提取 | Hook 事件 |
| 会话结束只留值得留下的 | 上下文压缩(compaction) |
| 网页内容不写入记忆 | 不可信输入隔离 |

## 十三、扩展体系:Skill、Command、Plugin、MCP、Bridge ✅

Tool 是手,Skill 是经验,Command 是按钮,MCP 是接外设的接口,Plugin 是装好的套餐,Bridge 是通向各个渠道的门。核心层稳定不动,新能力从扩展层进来。

### 概念边界

| 概念 | 一句话 | 谁触发 | Lumi 里的例子 |
| --- | --- | --- | --- |
| Tool | 一个能力(带副作用级别的函数) | 模型调用 | web\_search、set\_reminder |
| Skill | 可复用的「做事方法」:指令 + 允许的工具 + 输出格式 | 模型按描述选用 | 读论文给 3 行摘要、追踪发布会、周回顾 |
| Command | 用户的快捷入口,绑定 Skill 或工具并预填参数 | 用户点击或输入 | 任务提示语「提醒我 · 周四上午」 |
| MCP | 接入外部工具和数据的标准协议 | 模型调用(经 Tool 包装) | 日历、邮箱、Notion、行情 |
| Plugin | 打包分发的单元 | 用户安装启用 | 「投资研究包」「学术包」 |
| Bridge | 连接外部渠道的适配层(收和发) | 渠道事件 | 微信、Telegram、邮件、推送 |

「聊聊 → 任务提示语」本质就是 Command:点一下,预填参数,交给 Skill 去做。

### Skill

格式类似 Claude Code 的 SKILL.md:

```
---
name: paper-summary
description: 读一篇论文或长文,输出 3 行摘要、关键数字和局限
allowed_tools: [web_fetch, read_card]
output_schema: task_result.summary_v1
---
步骤、判断标准、示例……
```

1. 渐进加载:上下文只常驻名称和描述,命中后才加载全文,Skill 再多也不撑爆上下文
2. Skill 只能收窄权限,不能放宽:allowed\_tools 是用户已有权限内的子集
3. Task 的 kind 模板就是 Skill:卡片里 suggested\_tasks 的预填参数指向某个 Skill

起步内置 5 个:paper-summary、event-tracker、topic-tracker、weekly-review、meeting-prep。新场景(出行、记账、学习计划)都是新增 Skill,不动核心。

### MCP

Lumi 作为 MCP 客户端,每个连接的服务器暴露的工具统一包装成 Lumi 的 Tool 定义,带上 side\_effect。

- 外部服务器自称的「只读」「破坏性」标注不可信:新接入的工具默认按 L2 处理(每次确认),经用户明确放行或平台审核后才降级
- 工具名带命名空间(mcp\_\_calendar\_\_create\_event),避免重名劫持
- 工具返回内容一律标记 untrusted
- 渐进授权:用户说「提醒我周四」时才申请日历权限
- 接入顺序:日历读 → 日历写 → 邮箱读 → 笔记类 → 其他,先读后写
- 后期可选:Lumi 自己提供 MCP 服务,让其他 Agent 读取用户的收藏与阅读清单(需用户授权)

### Plugin

| 组成 | 说明 |
| --- | --- |
| Skills | 领域做事方法 |
| Commands | 对应的快捷入口 |
| MCP 连接配置 | 需要的外部数据源 |
| Hooks | 如该领域的卡片校验规则 |
| 卡片模板 | 该领域特有的高亮类型(如财报的「营收 / 同比」) |
| Agent 角色 | 如该领域的专属研究员 |
| 权限清单 | 安装时展示要用哪些工具、访问什么数据 |

示例:「投资研究包」= 财报摘要 Skill + 行情 MCP + 「营收同比」卡片模板 + 投资领域研究员。

- 安装前展示权限清单,用户同意才启用,可单独禁用
- Plugin 的 Hook 不能放宽核心权限:核心 Hook 先执行,deny 规则永远优先
- 版本固定、签名校验;Plugin 内脚本在沙箱里运行
- 审计和成本都带 plugin\_id,可定位问题,有一键停用开关

### Bridge

入站:用户通过微信、Telegram、邮件、语音等对 Lumi 说话。出站:推送、邮件、日历写入等。

1. 统一消息格式:适配器把消息规范化为 {user, channel, text, attachments, card\_ref},核心引擎不关心消息从哪来
2. 身份绑定:渠道账号与 Lumi 账号绑定后,才被当作用户本人的指令
3. 区分「本人说的话」和「转发进来的内容」:转发的邮件、文章是不可信数据,可能含恶意指令,按 untrusted 处理
4. 渠道能力矩阵:App 有完整卡片,短信只有纯文字,邮件可排版,出站按能力降级渲染
5. PreSend Hook 统一把关免打扰时段、每日推送上限、重复去重

### 整体分层

```
[渠道层]   App / 网页 / 推送 / 邮件 / 微信 …   ← Bridge
              ↓ 统一消息格式
[交互层]   Command(用户入口)  ·  Inbox
              ↓
[核心层]   Agent loop · Tool System · Governance · Work System · Memory
              ↑ 扩展点
[扩展层]   Skill · MCP(外部工具)· Hook · Agent 角色 · 卡片模板
              ↑ 打包分发
           Plugin
```

### 开发顺序

1. Command:任务提示语
2. 内置 Skill:先做 3 到 5 个
3. MCP:日历读,再日历写
4. Bridge:推送与邮件
5. Plugin 打包格式与权限清单
6. 插件市场(最后,甚至可以不做)

## 十四、MVP 范围、技术选型与里程碑 ✅

MVP 的标准是每个里程碑都能跑通、能演示、对应一个底层概念;M0 到 M2 不需要前端,用命令行和 JSON 验证流水线。

### MVP 范围

| 做 | 不做(后置) |
| --- | --- |
| Agent loop、搜索工具、日报流水线 | 插件市场 |
| 多领域 subagent 并行 + 总编辑 + 降级 | 微信等 IM Bridge |
| 开屏引导、全屏阅读、反馈、Inbox | 语音播报 |
| 聊聊 → 任务确认卡 → 提醒与定时日报 | 付费与额度体系 |
| 权限 L0 到 L2、审计日志 | 完整的生成式插画(先用模板图) |
| 画像 + 兴趣模型 + 记忆页 + 追踪话题 | 多端同步 |
| 3 个内置 Skill、日历 MCP、推送 | Plugin 打包(最后做) |

### 技术选型

| 层 | 选择 | 理由 |
| --- | --- | --- |
| 语言 | TypeScript 全栈 | 工具 schema(zod)与卡片 schema 前后端共享类型;Claude Code 本身也是 TS,便于对照 |
| 前端 | Next.js + Tailwind;粒子用 Canvas 或 three.js;猫头鹰动效用 Lottie | 动效重但独立,不影响核心 |
| 实时 | SSE 推送 Agent 事件 | 对应「正在搜索…」等待态,比 WebSocket 简单 |
| 数据库 | Postgres + pgvector | 报告、任务、记忆、审计日志一套存,记忆检索用向量 |
| 任务与调度 | 持久化任务队列(如 pg-boss) | 幂等键、重试、定时、优先级都需要,不用内存定时器 |
| 搜索 | Anthropic API 的 web\_search 工具或独立搜索 API | 工具层做成可替换 |
| 推送 | Web Push(PWA),邮件后补 | 手机端优先,PWA 成本最低 |

Agent loop 先手写,不直接用现成 SDK:先理解「调用模型 → 解析工具调用 → Hook → 权限 → 执行 → 回填」,再对照 Claude Agent SDK 看它替你做了什么。

### 评测集(从 M1 起)

内容类产品的质量必须可量化。建一个小评测集(几十条候选事件 + 期望行为),自动统计:

- 字数合规率、source\_refs 覆盖率、要点可溯源率
- 重复率(近几天已推)、领域保底是否满足
- 失败降级触发率、单份报告成本与耗时

每次改 prompt 或换模型都跑一遍。面试时能说清「我怎么知道它变好了」。

## 十五、开发工作流 ✅

用 Lumi 自己的治理思路管理 Lumi 的开发:spec 在仓库里,每个角色职责固定,CI 当裁判,按风险分级决定能否自动合并,写的人不审自己的活。

### 角色分工

| 角色 | 谁 | 职责 |
| --- | --- | --- |
| 出题人 | 我(项目负责人) | 提需求、拍板、审设计稿与文案、冻结契约、批准高风险变更 |
| 主控 | Claude | 整理需求、只读调研、出方案、出设计原型与文案、定接口与验收标准、拆任务包、需求层验收 |
| 实现者 | Cursor | 按任务包实现后端与前端,自测并交回执,按评论修改 |
| 审查者 | Kimi | 独立做代码层审查(bug、安全、风格、测试覆盖),只评论不改 |
| 裁判 | CI(确定性代码) | lint、类型检查、测试、评测集、冒烟,不过不能合并 |

关键决策:

- **设计稿由 Claude 出,Cursor 不画稿**:设计稿是可丢弃的原型(可点击 HTML + 文案表),不是生产代码,避免原型被当成实现;定稿后产出「设计转组件」对照表(组件树、状态、文案、设计 token、动效参数)交给 Cursor。猫头鹰与粒子 Lumi 的最终动效资产来源单独定
- **前端与验证拆成四件**:Cursor 写前端;CI 跑测试(Cursor 自测不算数,必须在干净环境再跑);Claude 做需求层验收(对照验收标准与设计稿,前端用截图对比);Kimi 做代码层审查
- **写的人不审自己的活**:同一模型的盲点重合,独立审查才抓得到「看起来对但没满足需求」;测试最好由与实现者不同的模型根据验收标准来写(先红后绿)

### 全流程

```
①需求 → ②调研 → ③方案 → ④设计 → ⑤契约 → ⑥派活 → ⑦实现 → ⑧验证合并 → ⑨发布核实
  我说   Claude   Claude   Claude   Claude   Claude   Cursor   CI + Kimi +    自动灰度
         只读     出选项   原型+文案  接口+AC  任务包   写+自测  Claude 验收     回滚、核实

人工门:        ★G1 拍板  ★G2 审稿  ★G3 冻结契约             ★G4 批准合并(仅高风险)
```

所有产物放进仓库 docs/requests/REQ-xxx/,形成可追溯链;Claude 不跨对话记忆,主控状态必须外置到仓库文件。

### 逐阶段

| 阶段 | 谁 | 产出 | 人工门 |
| --- | --- | --- | --- |
| ① 需求与分流 | 我说,Claude 整理为需求单(目标、成功指标、不做什么、约束),有歧义最多问 3 个问题 | request.md;按大小分级(Bug / 小 / 中 / 大) | 小需求跳过④ |
| ② 调研(只读) | Claude 查代码、数据、线上 | findings.md,每条结论带证据(文件与行号、查询与结果、日志链接) | 无 |
| ③ 方案 | Claude 出 2 到 3 个选项,含取舍、风险、回滚、指标 | proposal.md;拍板后写 decision.md(选了什么、为什么、没选什么) | G1 拍板 |
| ④ 设计 | Claude 出线框到可点原型 + 文案表 + 状态清单(空、加载、失败、降级)+ 动效规范 | design/v1、v2…、copy.json;我审交互与文案,取舍后改稿并记录 | G2 审稿 |
| ⑤ 契约 | Claude 定接口与 schema、数据迁移、编号验收标准 AC、非功能要求(性能、成本、权限、隐私)、变更风险等级、发布与回滚判据;同时先写验收测试骨架(先红) | spec.md | G3 冻结 |
| ⑥ 派活 | Claude 拆任务包并画依赖顺序:契约与迁移 → 后端 → 前端(对 mock)→ 集成 | tasks/\*.md,每包一个 PR、约 400 行内、限定可改文件范围 | 无 |
| ⑦ 实现 | Cursor 按任务包实现,先自测(限轮数),交标准回执 | PR 描述中的回执 | 无 |
| ⑧ 验证与合并 | 自动检查 → Kimi 审查 → Claude 验收 → Cursor 按评论修(最多 3 轮)→ 合并 | 检查报告、审查评论、验收清单 | 高风险变更 G4 |
| ⑨ 发布与核实 | 预发 → 冒烟 → 灰度 → 全量 → 核实线上 → 结果回写并通知我 | verification.md | 无 |

补充的关键环节:

1. **分流**:小改动走快速通道,避免每个文案修改都走全流程
2. **证据化调研**:结论必须附证据
3. **决策记录**:记下没选的方案与理由,防止翻案,也是面试素材
4. **状态清单与文案外置**:设计稿画出空、加载、失败、降级;文案放进 copy.json,改文案不改代码
5. **契约冻结与变更流程**:G3 之后改验收标准必须回到 G3
6. **任务包与回执模板**:回执必须写明做了什么、没做什么、偏离 spec 之处及原因、测试结果、新发现的风险、待确认问题
7. **先写测试后写实现**:验收测试在⑤以红色状态存在,Cursor 的目标是让它变绿
8. **灰度、回滚与线上核实判据**在⑤就写进 spec
9. **回写**:上线结果写回 REQ 文档并通知我,这一轮才算结束

### 风险分级与自动合并

| 级别 | 例子 | 流程 |
| --- | --- | --- |
| R0 低 | 文案、样式、文档、测试 | 自动检查与 Kimi 审查通过即自动合并 |
| R1 中 | 普通功能逻辑 | 检查、Kimi、Claude 验收都通过后自动合并,灰度发布,指标异常自动回滚 |
| R2 高 | 权限与治理代码、数据迁移、对外动作(L2)、成本与模型选择、提示注入防护 | 必须我批准(G4) |

核实线上用确定性判据:错误率、延迟、成本,以及评测集指标(字数合规率、溯源率、降级触发率),与上线前基线对比;回滚由阈值自动触发,AI 只负责读结果、写结论并通知我,不由 AI 决定是否回滚。

### 仓库骨架

```
lumi/
├─ AGENTS.md                  项目宪法,所有 Agent 先读
├─ .cursor/rules/*.mdc        架构、测试、风格细则
├─ .cursor/cli.json           CLI 权限(白名单与禁区)
├─ docs/design/lumi.md        设计文档导出为 Markdown
├─ docs/requests/REQ-xxx/     每个需求的全链路产物
├─ specs/                     一个 PR 对应一份 spec
├─ evals/                     评测集
└─ .github/
   ├─ workflows/ci.yml
   ├─ workflows/kimi-review.yml
   └─ pull_request_template.md
```

- 设计文档必须导出进仓库:Agent 读不到外部文档,仓库里没有的东西就不存在
- AGENTS.md 写得短而硬:项目一句话、目录结构、常用命令、必须遵守的架构约束(读写分离、Agent 工具白名单、字数限制进 schema)、禁止事项(不改权限逻辑、不提交密钥)、PR 要求

spec 模板:背景与目标(引用设计文档章节)/ 范围(做与不做)/ 接口与数据结构 / 验收标准(编号 AC-1、AC-2,每条可测试)/ 测试要求 / 涉及文件与依赖 / 完成定义(CI 通过 + 验收标准全部覆盖 + 变更约 400 行内)。验收标准编号让 Kimi 与 Cursor 的评论、修改都能精确引用。

### Cursor 与 Kimi 的接入方式

**Cursor 从 spec 到 PR(由简到全自动):**

| 方式 | 做法 | 阶段 |
| --- | --- | --- |
| 本地 Agent | plan 模式读 spec,确认计划后实现,手动开 PR | 第一周 |
| Cloud Agents(原 Background Agents) | 在云端虚拟机运行,完成后自动开 PR | 日常使用 |
| API 或 Automations 触发 | Cloud Agents API 创建 Agent 并可设置自动建 PR;Automations 按计划或事件(GitHub、Slack、webhook、Linear 等)触发 | 流程稳定后 |

另一条路:Cursor CLI 以无头模式在 GitHub Actions 中运行,用权限配置限定可读写路径并禁止直接使用 git 与 gh。

**Kimi 审查(两条路):**

- 社区的 kimi-bugbot GitHub Action(第三方,使用前先审代码与权限要求)
- 自己写 workflow(推荐):调用 Kimi Code CLI 或兼容 OpenAI 的 API,prompt 完全可控。要点:输入 spec + diff + AGENTS.md;按 AC 编号逐条给出满足 / 不满足 / 无法判断;单列缺失测试、与设计文档冲突、安全问题(是否违反读写分离与权限分级);只评论不改代码

API 基础地址、模型名与计费以各家官方控制台和文档为准,上线前先核对。

**CI 与分支保护:** CI 必跑 lint、类型检查、单元测试、评测集门槛;必须通过检查、至少 1 人批准,Agent 不能直接推 main、也不能自己合并。

**防失控三条限制:** review-fix 最多 3 轮,超了停下等我;每个 PR 约 400 行以内,超了要求拆分;设置成本上限。

**安全:** 密钥放 GitHub secrets,不给 Agent 读 .env;PR 描述、Issue、评论都是不可信输入,不能被 Agent 当指令执行(与 Lumi 的读写分离同理);保持不对来自 fork 的 PR 触发自动化。

### 分阶段启用

| 阶段 | 启用的环节 |
| --- | --- |
| M0 到 M2(无前端、无线上) | ①③⑤⑥⑦⑧,跳过④设计与⑨线上核实 |
| M3(有前端) | 加入④设计稿、截图对比 |
| M4 起(有线上) | 加入⑨灰度、核实、回滚 |

节奏:第 1 周半自动(本地 Cursor 实现 → 手动开 PR → 手动触发 Kimi 审查),把 AGENTS.md、spec 模板、审查 prompt 调顺;第 2 周起 Cloud Agent 开 PR + Kimi 走 GitHub Action + CI 全接入;之后用 API 或 Automations 批量触发多份 spec。前几份 spec 的问题多半出在 spec 太模糊,而不是模型不行。

## 十七、面试可能被问到的问题(持续补充)

- 为什么从「日报」切入而不是直接做万能助理?(高频、低风险、可量化反馈、天然产生用户画像)
- 怎么保证内容不胡编?(要点级溯源、置信度标注、校验 Hook)
- 怎么控制成本?(模型分级、L2 懒生成、缓存、固定条数)
- 怎么处理信息茧房?(惊喜条、探索信号、领域保底配额)
- 为什么任务要先出确认卡?(Governance:复述理解、声明权限、可编辑后再执行)

* 为什么把研究、选材、写作拆成不同角色?(分离关注点:研究员只找料,总编辑统一取舍,Writer 只能基于材料写,降低编造风险)
* 多用户下怎么控制成本?(按领域共享候选池,个性化只在选材和写作阶段,总编辑以外用小中档模型)
* 某一步失败了怎么办?(分级降级 + 截止时间驱动发布,用户永远不会面对空白)

- 怎么防止网页里的恶意指令劫持 Agent?(读写分离:读网页的 Agent 没有写入工具,工具返回内容标记为 untrusted)
- 权限怎么设计?(按 side\_effect 分 L0 到 L3,L2 对外动作永远逐次确认,规则 deny > ask > allow)
- Hook 和让 LLM 判断权限相比好在哪?(确定性、可审计、不可被提示词绕过)

* 为什么把 Task 和 Run 分开?(定义与执行分离,重试、审计、成本都落在 Run 上,Task 保持干净)
* 调度怎么保证不重复、不遗漏?(至少执行一次 + 幂等键;错过策略按任务类型区分)
* 追踪话题怎么避免变成骚扰?(默认沉默,只有重大更新才进报纸,冷了降频,主动提议收尾)
* 多个 Agent 并行写同一份数据怎么办?(Run 先写草稿再原子提交,共享数据乐观并发)

- 记忆怎么设计才既「越用越准」又可控?(三层:画像用户所有、兴趣模型代码更新、事实带来源与过期;全部可见可改可真删除)
- 为什么兴趣权重不让 LLM 直接写?(不稳定、不可审计;数值由反馈事件按公式更新)
- 怎么防止记忆被污染?(网页内容永不写入记忆;推断需证据累计;敏感类默认不记)

* Tool、Skill、Command、MCP、Plugin、Bridge 怎么区分?(手、经验、按钮、外设接口、套餐、渠道门;Skill 只能收窄权限不能放宽)
* 接第三方 MCP 怎么保证安全?(自称的只读标注不可信,新工具默认 L2 逐次确认,返回内容 untrusted,渐进授权)
* 怎么让产品从日报长成生活助理而不改核心?(核心层稳定,新能力以 Skill、MCP、Plugin 从扩展层进入)
* 转发进来的邮件或文章怎么处理?(区分本人指令与转发内容,后者按不可信数据)

- 为什么 Agent loop 先手写而不用现成 SDK?(目的是理解底层:模型调用、工具解析、Hook、权限、回填;再对照 SDK 看它封装了什么)
- 你怎么知道改 prompt 后变好了?(评测集:字数合规率、溯源率、重复率、降级触发率、成本与耗时)
- 为什么 M0 到 M2 不做前端?(先把流水线用命令行和 JSON 验证,trace 比界面更能说明对底层的理解)

* 你怎么用 AI 协作开发?(Claude 主控:调研、方案、设计、契约;Cursor 实现;Kimi 独立审查;CI 当裁判;四个人工门与 R0 到 R2 风险分级)
* 为什么实现和审查用不同模型?(同一模型盲点重合;测试作者与实现者分离,先红后绿)
* 怎么防止 AI 流水线失控?(review-fix 最多 3 轮、PR 约 400 行、成本上限、Agent 不能合并 main、高风险变更必须人批)
* 怎么保证 AI 不被 PR 或 Issue 里的恶意文字劫持?(这些都是不可信输入,与 Lumi 读写分离同理;不对 fork 触发自动化)
* 上线后怎么确认没出问题?(确定性判据对比基线,阈值自动回滚,AI 只读结果并写结论)
